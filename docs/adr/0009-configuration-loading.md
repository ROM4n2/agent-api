# ADR-0009：配置加载方式（环境变量 vs 配置文件）

- **日期**：2026-09-02
- **状态**：已接受

## 背景

用户反馈：本地起服务每次都要设 `DEEPSEEK_API_KEY`、`API_AUTH_KEY` 两个环境变量，太麻烦，
问能不能改成从网页输入，或者写进一个 `yaml` 文件。

同时排查出一个真实故障：Demo 页面所有字段显示 `undefined`。根因是 `store.Task` 没有显式
`json` tag，`encoding/json` 用 Go 字段名序列化成 `ID/Status/...`，而前端按小写 `task.status`
读取。字段名属于**对外契约**，当时却由语言默认行为隐式决定。

## 双镜评估

### 🎯 产品与使用体验层

- 环境变量是"每次都要做一遍的事"，换一个终端就得重来，本地开发摩擦明显。
- 网页输入 key 只能解决**服务端鉴权**（`API_AUTH_KEY`）。`DEEPSEEK_API_KEY` 是服务端调 LLM
  用的，不该经过浏览器，否则等于把上游密钥暴露给任何能打开页面的人。
- 配置文件是"配一次就忘掉"的方案，本地开发体验最好；Docker/CI 场景仍用环境变量。

### 🤖 技术与工程层

- 引入 `gopkg.in/yaml.v3` 能拿到完整 YAML 能力，但会打破项目"零第三方依赖"的定位
  （ADR-0004 的 YAGNI 纪律，也是 README 里写明的卖点）。
- 标准库没有 YAML 解析器。要么加依赖，要么自己解析一个子集。
- 配错 key 导致"静默忽略"是最难排查的一类问题：拼错 `deepseek_apikey` 若不报错，
  用户会看到服务正常启动但每个任务都失败。

## 决策

1. **配置来源改为两路，环境变量优先**：`环境变量 > config.yaml > 零值`。
   文件可选，不存在不算错误，纯环境变量的用法不受影响。
2. **用标准库解析扁平配置子集**，不引入 YAML 依赖。
   只支持每行一个 `key: value`、`#` 注释、引号包裹的值；
   遇到嵌套、列表、缺冒号的行或未知 key 一律**报错退出**，绝不静默忽略。
3. **`DEEPSEEK_API_KEY` 不经过浏览器**。网页 token 框只用于 `API_AUTH_KEY`，
   值存在浏览器 `localStorage` 里，填一次即可复用。
4. **鉴权密钥改为显式注入**：`api.NewHandler(s, p, authKey)`，
   `api` 层不再直接读环境变量。配置来源收敛到 `main` 一处，测试可直接注入不同密钥。
5. **序列化契约定死**：`store.Task` 加显式 `json` tag（小写），
   并用 `api/task_contract_test.go` 钉住，防止再次出现前后端字段名不一致。

## 后果

- ✅ 本地开发配一次 `config.yaml` 即可，不必每次设环境变量；Docker/CI 仍走环境变量。
- ✅ 零第三方依赖的定位保住，代价是只支持扁平配置子集（已写在 `config.yaml.example` 里）。
- ✅ 配置写错会启动失败并指出行号，不会静默用错值。
- ✅ Demo 的 `undefined` 故障修复，且有了回归测试兜底。
- ⚠️ 若将来需要嵌套配置，应直接引入 `gopkg.in/yaml.v3` 并废弃自研解析器，
  届时另立 ADR 修订本决策（本 ADR 的解析器定位是"两个 key 的临时务实方案"）。
