# ADR-0006：Worker 并发上限（硬编码 3 vs 可配置）

- **日期**：2026-09-02
- **状态**：已接受

## 背景

`main.go:40` 写死 `worker.NewPool(3, s, llm.NewClient(cfg))`：并发 worker 数固定为 3。
这个数字同时决定了**同时执行的 LLM 请求数**与**队列缓冲大小**（ADR-0003 决策 4：
缓冲 = worker 数）。本 ADR grill：3 从哪来？是否应做成可配置（env/flag）？

## 双镜论证

### 🎯 产品与用户体验层

- **数字的含义**：3 限的不是 goroutine，而是**同时在飞的 LLM 调用**（ADR-0002 精神）。
  它直接对应上游速率限制与账单成本——这是业务调参，不是性能调参。
- **用户对旋钮的认知成本**：对演示/面试项目，暴露 `WORKER_COUNT` 只是多一个
  "我该填几" 的困惑。绝大多数使用者不会、也不该关心这个数。固定 3 是"开箱即合理"的默认。
- **可观测性预期**：固定值让行为可预测，便于在文档/面试中给出确定答案（"并发 3，超出排队"）。

### 🤖 技术与系统工程层

- **魔法数字**：`3` 是 tuning 常量。GO-STANDARDS 未强制禁止，但硬编码意味着
  改并发必须改代码重编译。若它真随部署环境变化，应外置。
- **它该听谁的**：上限应由**下游 LLM 速率限制 / 预算**决定，而非本机 CPU 核数。
  因此它是"部署期业务参数"，天然适合 env 注入，而非编译期常量。
- **实现成本极低**：`os.Getenv` + `strconv.Atoi` 或 `flag.Int` 三五行即可，
  不会引入新依赖，符合 Ladder of Reuse Level 1（stdlib）。
- **与 ADR-0004 的联动**：一旦进入"多实例部署"，每实例并发数很可能需按实例规格/配额分别设定，
  届时硬编码必然不够，配置化是顺理成章的演进。

## 候选方案

- **方案 A（推荐）**：MVP 保持硬编码 `3`，但在 `main.go` 用具名常量（如 `defaultWorkerCount = 3`）
  并加注释说明其"对应 LLM 并发配额"的语义。
- **方案 B**：env 可配（`WORKER_COUNT`，缺省 3），启动时校验下界 ≥1。
- **方案 C**：命令行 flag 可配（`-workers`，缺省 3）。

## 决策

**采用方案 A：MVP 硬编码 3（提升为具名常量 + 注释语义）。**

理由：当前阶段无真实多环境部署，配置化是 YAGNI；固定值让行为可预测、文档确定。
但把裸 `3` 改为带语义注释的命名常量，消除"魔法数字"嫌疑，且为将来外置留好锚点。

**触发配置化的信号**（出现其一则升级到方案 B/C，并另立 ADR）：
1. **真实速率限制/预算压力**：需要根据上游配额动态调整并发 → env 注入最合适。
2. **多实例部署**（ADR-0004 触发）：不同实例按规格/配额设不同并发 → 必须可配。
3. **压测驱动调优**：实测发现 3 不是最优，需频繁试不同值 → 配置化免去反复编译。

## 与已学知识的映射

| 设计点 | 已学技能 |
|--------|---------|
| 魔法数字 → 具名常量 | GO-STANDARDS 2.x 命名 |
| 业务调参 vs 性能调参 | ADR-0002 并发语义 |
| YAGNI / Ladder Level 1 | 1.0 指导原则 |
| env/flag 配置（stdlib） | 标准库零依赖 |

## 后果

- ✅ 开箱即用、行为可预测、文档/面试答案确定。
- ✅ 命名常量消除魔法数字，语义自解释。
- ✅ 零新依赖、零配置面。
- ⚠️ 改并发需改码重编译——仅在对触发信号敏感时才成问题。
