# ADR-0004：不引入数据库 / 消息队列（持久化取舍）

- **日期**：2026-09-02
- **状态**：已接受

## 背景

ADR-0003 决策 2 标注「内存存储、重启即丢失」为已知限制，决策 4 的修复路线提到
「长期换 SQLite/Redis 持久化队列」。这容易被误读为**既定路线图**。
本 ADR 显式 grill 这个 fork：**当前是否应该引入 DB 或消息队列？**

## 双镜论证

### 🎯 产品与用户体验层

- **真实痛点 vs 伪需求**：任务平均生命周期 < 1 分钟，调用方提交后立刻轮询拿结果。
  服务重启丢失少量在飞任务，对 MVP/面试项目**零用户可感知代价**。
  没有真实用户要求「任务跨重启存活」——这是想象中的需求。
- **认知摩擦**：引入 DB 带来迁移、schema、连接管理；引入 MQ 带来 broker 运维。
  对演示型项目，这把"能跑的 demo"变成"要运维的系统"，反而抬高交付摩擦。
- **心智模型**：调用方走的是「提交→轮询」模型，本就不隐含「job system 级别的持久保证」。

### 🤖 技术与系统工程层

- **资源成本错配**：当前 `map + Mutex`（ADR-0002）已正确且极简。SQLite 引入事务边界、
  WAL、锁竞争；Redis 引入每次操作的网络 RTT。为 <1 分钟的任务付出持久化代价，本末倒置。
- **新故障模式**：DB/MQ 宕机 = 整个服务不可用。内存方案的唯一失败是「重启丢任务」，
  而这是**可接受的、有界的**失败，不是雪崩。
- **The Ladder of Reuse（RFC 2119 MUST）**：
  - Level 0（YAGNI/用户价值）：无真实持久化需求 → 不值得做。
  - Level 1（Stdlib/现有代码）：`map + Mutex` 已是标准库 3 行方案，无需新代码。
  - Level 2（现有依赖）：引入需**新增依赖**（sqlite 驱动 / redis 客户端），违反「无必要不加依赖」。

## 候选方案

- **方案 A（推荐）**：保持纯内存（store map + channel queue），不引入任何外部存储。
- **方案 B**：SQLite 持久化任务状态、保留 channel 队列。能跨重启存活，但队列仍不持久。
- **方案 C**：Redis 同时持久化任务 + 做 durable queue。完整解，但引入 broker 运维。
- **方案 D**：成熟 job-queue 框架（asynq / bull）。过度工程，远超项目规模。

## 决策

**采用方案 A：MVP 不引入 DB / 消息队列。**

ADR-0003 决策 4 中的「长期持久化队列」**不是既定路线，而是条件触发项**——
只有出现下列任一信号才重新评估（届时另立 ADR）：

1. **任务耗时变长**（分钟级）且用户明确不能容忍重启丢失；
2. **多实例部署**（水平扩容），内存状态无法在实例间共享；
3. **可观测性/审计**要求任务历史落库。

在未触发前，坚持 YAGNI：内存方案零依赖、零运维、逻辑聚焦于并发与接口本身。

| 设计点 | 已学技能 |

## 后果

- ✅ 零外部依赖，部署只需一个二进制 + 一个 env。
- ✅ 失败模式有界、可理解，无级联雪崩风险。
- ✅ 逻辑聚焦并发与 HTTP 接口，契合学习与面试目标。
- ⚠️ 重启丢全部任务——已声明为可接受限制。
- ⚠️ 队列满退化为阻塞 handler（ADR-0003 决策 4）——短期 503 快速失败仍可按需补。
