# ADR-0005：任务结果获取 —— 轮询 vs 服务端推送

- **日期**：2026-09-02
- **状态**：已接受

## 背景

客户端提交任务后需要拿到结果。当前实现是**客户端轮询** `GET /tasks/{id}`
（ADR-0002 决策 5）。另一选项是**服务端推送**：长轮询 / SSE / WebSocket，
由服务器在任务完成时主动把结果推给客户端。本 ADR grill 这一分发模型的选择。

## 双镜论证

### 🎯 产品与用户体验层

- **延迟敏感度**：LLM 任务本身耗时 10–60s，客户端本来就预期"等一会儿"。
  几秒一次的轮询延迟相对任务总时长可忽略，推送的"瞬时通知"在此场景无感知收益。
- **客户端心智与成本**：轮询是「提交→循环 GET→拿到 done」的直白模型，
  任意语言几行代码即可，且 `GET` 幂等、可重试、可缓存。推送需 `EventSource` /
  `WebSocket` 握手、断线重连、消息序号——客户端复杂度陡增。
- **失败可恢复性**：轮询天然容错——客户端任何时候重发 `GET` 都能恢复状态，
  不依赖连接存活；推送一旦断线需重建会话并续传，否则丢结果。

### 🤖 技术与系统工程层

- **连接资源**：推送（SSE/WS）为每个客户端长期占用一条连接。当前单实例内存架构下
  体量小无所谓，但**跨负载均衡器**时 SSE/WS 需粘性会话（sticky session）或网关支持，
  引入部署约束。轮询是无状态短请求，天然对 LB 友好。
- **YAGNI / The Ladder of Reuse**：轮询复用现有 `GET /tasks/{id}` 端点，零新协议、零新依赖。
  推送需新增协议层与（可能的）升级握手处理，违反 Level 0/2。
- **与异步架构的一致性**：任务本就是 fire-and-forget 异步模型，
  「稍后主动来查」比「服务器记住你是谁并回调你」更契合解耦初衷。

## 候选方案

- **方案 A（推荐）**：保持客户端轮询 `GET /tasks/{id}`。
- **方案 B**：长轮询（hold 请求直到状态变化或超时）。降低轮询空转，但占用 handler 连接更久。
- **方案 C**：SSE 单向推送。任务完成/进度时 server push；仍需客户端建连与重连。
- **方案 D**：WebSocket 双向通道。可进一步做 token 流式输出，但协议与状态管理最重。

## 决策

**采用方案 A：MVP 维持客户端轮询。**

理由：任务耗时本来就长，轮询延迟无感；`GET` 幂等可重试、对 LB 友好、
零新依赖，且最契合「异步解耦」的架构语义。推送的复杂度在此阶段是过度工程。

**触发重估的信号**（出现其一则另立 ADR 考虑升级）：
1. **UX 要求低延迟实时进度**（如前端要展示"生成中…"的流式 token）→ 走方案 D + 改造 `llm.Client` 契约（当前 `Chat` 返回完整字符串，需改为流）。
2. **客户端规模变大**，轮询空转请求成为可观的负担 → 评估方案 B/C 降低请求数。
3. **多实例部署**且需推送 → 必须配套粘性会话或消息总线，届时与 ADR-0004 的持久化触发一并评估。

## 后果

- ✅ 客户端极简、可重试、跨语言零成本。
- ✅ 服务端无状态、对负载均衡与重启友好。
- ✅ 零新依赖、零协议层。
- ⚠️ 轮询有空转请求（任务未完成时的重复 GET）——当前体量无影响。
- ⚠️ 无法推送中间进度/流式 token——如需则触发方案 D 升级。
