# ADR-0007：项目简历定位与优化路线

- **日期**：2026-09-02
- **状态**：已接受（P0 / P1 已于 2026-09-02 实施完成）

## 背景

用户问：**当前 agent-api 是否足以作为面试简历项目？不够的话如何优化？**
这个问题同时拷问产品定位与技术广度。下面用双镜评估现状并给出分级优化路线。

## 双镜评估：现状成色

### 🎯 产品与简历定位层

**已具备的卖点（真实、可讲）**
- 异步任务 + Worker Pool：goroutine / channel / 并发上限都有**真实动机**（限 LLM 成本，非限 goroutine）。
- 并发安全：Store 用 Mutex 全段加锁，`Get` 返回值副本消除 data race。这是面试高频题，代码正确。
- 依赖倒置：`worker` 定义 `chatter` 接口、注入 `llm.Client`，mock 可脱离网络跑单测。
- 工程素养：**25 个单测全绿**（含 `httptest` 端到端集成测试与 benchmark）、注释讲"为什么"、优雅停机用 context cancel、错误脱敏。
- **最大差异化**：配套 8 篇 ADR，能当场讲清每个决策的 trade-off。

**致命短板（面试会被追问的弱点）**
1. **命名与实质错位**：叫 "agent-api"，但只是"LLM 聊天代理的异步封装"，**没有真正的 agent 行为**
   （无工具调用 / 多步规划 / 反思循环）。面试官问"agent 在哪"，答不上来会塌房。
2. **广度偏窄**：无持久化、无鉴权、无限流、无中间件、无可观测性（metrics/trace）、无流式。
   暴露的 Go 知识面局限于"并发 + HTTP 基础"。
3. **不可演示**：只有一个 curl/Invoke-RestMethod 验证，缺一个能一眼看懂成果的前端或 demo 脚本。

> 1–3 是 2026-09-02 评估时的原始记录，保留原样以呈现「评估 → 决策 → 落地」的过程。
> P0/P1 落地后 1 与 3 已消除，2 已补齐大部分，见文末「执行状态」。

### 🤖 技术与系统工程层

- **代码质量**：符合 GO-STANDARDS，零魔法数字待治理项（ADR-0006 已规划）、零 lint 风险。
- **测试深度**：单测覆盖核心路径，但**缺集成测试**（真 HTTP 端到端）、**缺 benchmark**（pool 吞吐）、
  缺 `httptest` 对 handler 的表驱动覆盖（当前 handler 测试已存在但可更全）。
- **可演进性**：ADR-0004/0005/0006 为持久化、推送、配置化写明了触发条件，后续改动照此评估。

## 结论

**足以作为"扎实的 Go 后端学习项目"，尚未达到"惊艳的简历旗舰项目"。**
当前成色 ≈ 中游简历项目：基础牢、思考深，广度与记忆点不足。优化方式是**补广度 + 消除命名错位 + 提升可演示性**，不推翻现有架构。

## 分级优化路线（按性价比排序）

### 🥇 P0（必做，低成本高收益）
- **消除命名错位**：要么改名为 `llm-task-api` / `async-llm-proxy`，要么**加真 agent 能力**
  （工具调用循环：让 worker 跑一个 "think → call tool → observe" 的 N 步循环）。后者收益最大。
- **加 HTTP 中间件链**：recover（防 panic 崩服务）、request-id、基础鉴权（Bearer/API key）、
  限流（token bucket）。这是"生产感"的最低门槛。

### 🥈 P1（强推荐，中成本）
- **可观测性**：暴露 `/metrics`（Prometheus 风格计数器：在飞任务数、完成/失败数、LLM 耗时直方图）；
  加 `/healthz` `/readyz`。
- **加一个极简前端或 demo 页**：单 HTML 文件提交 prompt + 轮询展示结果，让面试官 10 秒看懂。
- **集成测试 + benchmark**：`httptest` 端到端跑一遍 `POST /run → 轮询 → done`；bench pool 吞吐。

### 🥉 P2（锦上添花，看时间）
- **流式输出（SSE）**：LLM token 边生成边推（联动 ADR-0005 触发信号，改造 `llm.Client` 契约）。
- **可选持久化开关**：按 ADR-0004 触发条件，提供 SQLite 后端（store 抽接口，内存/SQLite 双实现），
  展示"我能做持久化，只是 MVP 故意不做"。加分项，非必需。

## 决策建议

**推荐先吃下 P0（尤其"真 agent 能力"或"改名"二选一）+ P1 的可观测性与 demo 页**，
即可从"中游"跃升为"有明确记忆点的上游项目"。P2 视面试时间线决定。

> 注意：优化时**守住 ADR-0004/0005/0006 的 YAGNI 纪律**。加功能是为展示能力，
> 每个新增项都应有对应 ADR 或注释说明"为什么此时做"。

## 执行状态（2026-09-02 更新）

- ✅ **P0 已完成**：真 agent 能力（工具调用循环，见 ADR-0008）；HTTP 中间件链（Recover / RequestID / 限流 / 鉴权）。
- ✅ **P1 已完成**：
  - 可观测性：`GET /metrics`（`sync/atomic` 计数 + Prometheus 文本格式，零依赖）、`GET /healthz`。
  - Demo 页：`GET /` 单页（`go:embed` 内嵌，离线可用），提交 prompt 并轮询展示结果。
  - 测试增强：`httptest` 端到端集成测试；`BenchmarkPoolEnqueue` ≈ 1.5 µs/op、`BenchmarkRunAgent` ≈ 84 ns/op。
- ⏳ **P2 待定**：SSE 流式 token；可选 SQLite 后端（store 抽接口，内存/SQLite 双实现）。
- 实施计划见 `docs/implementation_plan_p1.md`。
- 当前测试基线：**25 passed / 0 failed**（api 9 · llm 3 · store 5 · worker 6 · metrics 2）。

## 后果

- ✅ 消除最大的面试塌房风险（agent 名实不符）。
- ✅ 广度从"并发单点"扩展到"并发 + 中间件 + 可观测 + 可演示"，覆盖更多面试题。
- ✅ 保留 ADR 资产，面试时可继续用叙事能力作差异化。
- ⚠️ P0/P1 新增了代码与文档，需维持 GO-STANDARDS 质量红线。指标与 Demo 均用标准库实现，未引入第三方依赖。
