# ADR-0010：引入 SQLite 持久化（opt-in）

- **日期**：2026-09-03
- **状态**：已接受
- ** Supersedes**：ADR-0004 中"重启丢全部任务"这一限制项（其余 YAGNI 结论不变）

## 背景

ADR-0004 把"内存存储、重启即丢失"列为可接受限制，并把持久化列为**条件触发项**
（任务耗时变长 / 多实例 / 审计需求）。本 ADR 在其之外新增一个触发动机：
**面试可辩护性与演示完整性**——"重启丢数据怎么办"是该项目最高频的追问，
把它从缺陷变成已实现的特性，直接提升简历答辩价值。

决策原则不变：仍坚持 YAGNI，但把持久化做成**可选、默认关闭**的能力，
不破坏"一个二进制即可跑、不配就不依赖存储"的轻量交付。

## 双镜论证

### 🎯 产品与用户体验层

- **可演示的健壮性**：配了 `db_path` 后，进程重启任务不丢，demo 与轮询链路更可信。
- **零强制成本**：不配 `db_path` 时行为完全等同 ADR-0004 的内存方案，默认路径零心智负担。

### 🤖 技术与系统工程层

- **依赖取舍**：选 `modernc.org/sqlite`（纯 Go 转译实现，无 CGO），
  保证克隆后直接 `go build` 无需 C 工具链；代价是 `go.mod` 引入该依赖及其转译子模块。
  这是项目**首个、也是唯一**的第三方运行时依赖，仅当启用持久化时才会真正被加载。
- **并发模型**：SQLite 单写者，并发写报 `database is locked`。
  用 `sync.Mutex` 把写操作整体串行化，读走 WAL 与写并发，规避锁竞争与写冲突。
- **抽象边界**：定义 `TaskStore` 接口，`Store`（内存）与 `SQLStore`（SQLite）双实现，
  worker/api 只依赖接口。后端可切换，测试仍可注入内存实现保持快速。

## 候选方案

- **方案 A（采用）**：SQLite 持久化任务状态，opt-in（`db_path`），内存为默认。纯 Go 驱动。
- **方案 B**：BoltDB/bbolt 嵌入式 KV。更轻的单一依赖，但无 SQL 可写、语义偏 KV。
- **方案 C**：JSON 快照落盘。零依赖，但重启恢复需整文件重写，崩溃一致性弱。
- **方案 D**：Redis 持久化队列。完整解，但引入 broker 运维，远超当前规模。

## 决策

**采用方案 A：引入 `modernc.org/sqlite` 作为 opt-in 持久化后端。**

- `config.DbPath` 为空 → 沿用 `store.Store`（内存，零存储依赖）。
- `config.DbPath` 非空 → 使用 `store.SQLStore`（SQLite，`PRAGMA journal_mode=WAL`）。
- 两套实现语义严格一致：终态只由 `Complete` 裁决、不存在 ID 返回 `ErrNotFound`、Get 返回副本。
- worker 并发上限、轮询模型、限流鉴权等其他设计**不受影响**，ADR-0002/0003/0005/0006 不变。

## 后果

- ✅ 重启不丢任务（启用时），直接回应高频面试追问。
- ✅ 默认路径仍零存储依赖、单二进制可跑；依赖仅在启用持久化时真正参与。
- ✅ `TaskStore` 接口抽象使后端可替换、测试可注入。
- ⚠️ 引入首个第三方运行时依赖，`go.mod` 体积增加（modernc 转译子模块）。
- ⚠️ 队列本身仍不持久：重启后已入队但未开始的任务会丢失（与 ADR-0004 队列结论一致，未改）。
- ⚠️ 写串行化下，极端高并发写入吞吐受单写者限制；当前 3 worker 场景远未触顶。
