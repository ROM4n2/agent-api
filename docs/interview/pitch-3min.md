# 3分钟项目陈述 (Project Pitch)

本文件整理自 2026-08-17 对话，用于面试前的项目陈述复习。

## 陈述结构与标准文案

### 1. 痛点与背景 (0:00 - 0:30)
> **核心痛点**：LLM 接口调用极慢（10s+），若使用同步 HTTP 请求，会严重阻塞连接资源，拖垮服务吞吐量。
> **架构方案**：设计了异步任务架构。在 [api/handler.go](../../api/handler.go) 中解析并创建任务后，立刻返回 `202 Accepted` 响应以释放 HTTP 连接，具体 LLM 请求在后台异步队列中执行。

### 2. 关键架构决策 (0:30 - 1:30)
> **决策一（轻量解耦）**：在 [worker/pool.go](../../worker/pool.go) 任务通道中只传递任务 ID，而不传递整个 Task 实体。Task 的唯一权威状态由存储层统一维护，传递 ID 可以避免状态副本冲突以及 channel 传递大对象的开销。
> **决策二（零依赖手写）**：在 [llm/client.go](../../llm/client.go) 中手写了对接 DeepSeek API 的 HTTP 客户端，而非直接引入官方 SDK。由于本系统只用到单次 chat completions 接口，手写客户端可以保持代码轻量（零依赖）、避免供应链风险，且通过配置 BaseURL 可以无缝切换任何 OpenAI 兼容的模型供应商。

### 3. 踩坑与排障 (1:30 - 2:30)
> **严重故障**：Goroutine 泄露导致的级联雪崩。最初没有为 `http.Client` 设置超时，其零值为永不超时。当上游大模型服务异常“沉默挂起”（TCP 连接已建立，但服务不返回任何数据）时，常驻 worker goroutine 会无限期阻塞。由于 worker pool 大小固定为 3，若三个 worker 全部僵死，缓存通道被塞满，新进的 HTTP 请求在调用 Enqueue 时会被彻底卡死在 Handler 中，最终演变为全站不可用。
> **修复方案**：在 [llm/client.go](../../llm/client.go) 级别配置 `Timeout` 兜底；在具体请求中传入带超时的 Context（`context.WithTimeout`），在任务完成或超时退出时利用 `defer cancel()` 彻底关闭底层的连接资源并回收 goroutine。

### 4. 技术债与后续迭代 (2:30 - 3:00)
> **妥协与迭代**：目前任务队列和存储层均在进程内存中，一旦重启进程数据将完全丢失。如果重来，会考虑引入 SQLite 或 Redis 对任务队列和状态进行持久化存储。同时，下一步需要完善优雅停机（Graceful Shutdown）机制，在进程退出时优先优雅取消（cancel）在飞的任务。

## 自检要点
- [ ] 表达时语速需平缓，卡在 2.5 - 3 分钟内完成。
- [ ] **级联故障链**必须描述清楚（沉默超时 -> worker 僵死 -> 队列满 -> handler 阻塞 -> 全站宕机）。
- [ ] **“队列传 ID 不传 Task”** 和 **“手写客户端零依赖”** 是架构亮点，必须重点强调。
