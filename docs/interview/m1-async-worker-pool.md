## Q1 讲讲你这个项目的架构，一个请求从进来到拿到结果经过哪些组件？

**考点**：能否讲清数据流向和 goroutine 边界。这题答得糊，后面所有问题都会被追着打。

**我的原答**（❌ 太笼统）：
> "api 处理命令，store 存储，pool 做相应动作。"

**扣分点**：只报了组件名，没讲**流向**、没讲**并发边界**。"pool 做相应动作"这句话，听不出答题者到底懂不懂。

**标准答法**：
> 请求打到 `api`，Handler 解析 JSON → 调 `store.Create` 拿到 taskID（状态 `pending`）→ 调 `pool.Enqueue` 把 **ID** 扔进 channel → **立刻**返回 `202` + taskID，HTTP 连接随即释放。
>
> 与此同时，`worker` 里 3 个**常驻** goroutine 在 `select` 上抢这个 channel，谁抢到谁把状态改成 `running`、执行任务、完成后改 `done`。
>
> 客户端之后靠 `GET /tasks/{id}` 轮询 `store` 拿状态和结果。

**必须出现的关键词**（漏一个就掉档）：
- 队列里传的是 **ID 而不是整个任务对象**（轻量、避免大对象在 channel 里拷贝）
- 返回 202 后 **HTTP 连接立即释放**，不占用连接资源
- worker 是 **常驻 goroutine**，不是每来一个任务新建一个

**常见追问**：
- *为什么队列传 ID 而不传 Task？* → task 的唯一权威状态在 store 里，传副本会导致两份状态不一致；且 ID 是字符串，拷贝成本恒定。
- *客户端轮询很浪费，有别的方案吗？* → SSE / WebSocket 推送，或 webhook 回调。轮询的优点是实现简单、对客户端和中间代理最友好，M1 阶段够用。

## Q2 为什么 `POST /run` 返回 202 而不是 200？

**考点**：是否理解 HTTP 状态码是**协议层的语义契约**，不是随便挑的数字。

**我的原答**（✅ 基本正确）：
> "202 是还没处理只是接受，200 是成功，/run 只是要做。"

**标准答法**：
> `200 OK` 的语义是"**请求已处理完成**，body 里是结果"。但异步接口返回时任务根本还没开始跑，body 里只有 taskID——用 200 是在**对客户端撒谎**。
>
> `202 Accepted` 的语义正是"**已接受，但处理尚未完成**"。它在协议层向客户端宣告：请拿着这个 ID 去别处查结果。这是异步 API 的标准做法。

**常见追问**：
- *为什么不用 201 Created？* → 201 表示"**资源已创建**"，通常配 `Location` 头指向新资源。严格说创建 task 记录用 201 也讲得通，但 201 强调的是"资源就绪"，而这里任务**尚未执行**，202 更准确地表达了"活还没干"。**能说出这个权衡比背下结论更值钱。**
- *客户端怎么知道去哪查？* → 规范做法是响应里带 `Location: /tasks/{id}` 头，客户端不用自己拼 URL。（当前实现只返回 JSON body 里的 `task_id`，属于可改进项。）

## Q3 `store` 为什么要加锁？不加会怎样？

**考点**：并发安全的**真实**理解。这题最容易答出"看起来对但其实不懂"的答案。

**我的原答**（❌ 理由错了）：
> "加锁是为了避免其他进程干扰，让当前 goroutine 顺利完成。"

**扣分点**：把锁理解成了"**独占执行权**"。锁保护的是**数据**，不是"顺利完成"——goroutine 不加锁也能顺利跑完，只是**数据被写坏了**。这是初学者最典型的误解。

**标准答法**：
> `store` 内部是 map，会被 3 个 worker goroutine 和 net/http 的每请求 goroutine **同时**读写。两个具体后果：
>
> 1. **Go 的 map 不是并发安全的**，多个 goroutine 同时写会直接 `panic: concurrent map writes`，进程当场崩溃。
> 2. 即使侥幸不崩，`Update` 是**读-改-写**三步复合操作（取出 Task → 改字段 → 写回），两个 goroutine 交错执行会**互相覆盖**对方的修改（丢失更新）。
>
> `sync.Mutex` 保证同一时刻只有一个 goroutine 能操作这个 map。这类问题靠 `go test -race` 自动检测。

**常见追问**：
- *为什么不用 `sync.RWMutex`？* → 读多写少时 `RWMutex` 能让读并行，是个优化方向。但本项目读写都很轻（内存 map 操作），锁竞争不是瓶颈，`Mutex` 更简单不易错。**先测出瓶颈再优化。**
- *为什么不用 `sync.Map`？* → `sync.Map` 只在"键集合稳定、读远多于写"的特定场景下更快，且它的 API 无法原子地做**读-改-写**（`Update` 需要）。加锁的普通 map 更适合。
- *`map[string]Task` 存值不存指针，为什么？* → 存值时 `Get` 返回的是**副本**，调用方拿到后随便改都不影响 store 内部数据，从设计上消灭了一整类数据竞争。存指针则会把内部状态泄漏给调用方。

## Q4 进程、线程、goroutine 有什么区别？

**考点**：Go 并发模型的地基。答错等于宣告"没搞懂并发"。

|  | 进程 process | 线程 thread | goroutine |
|---|---|---|---|
| 内存空间 | **独立**，互不可见 | 共享所属进程的内存 | 共享所属进程的内存 |
| 谁调度 | 操作系统内核 | 操作系统内核 | **Go 运行时（用户态）** |
| 创建开销 | 最大（MB 级 + 内核介入） | 大（默认栈 1~8MB） | **极小（初始栈 2KB，按需增长）** |
| 切换开销 | 最大（陷入内核） | 大（陷入内核） | **小（用户态切换，不进内核）** |
| 实际数量级 | 几十~几百 | 几百~几千 | **几十万~百万** |

**一句话版本**（可直接背）：
> 进程是**资源隔离**的单位，线程是**内核调度**的单位，goroutine 是 **Go 运行时调度**的用户态轻量线程——创建和切换成本比线程低约两个数量级，所以 Go 敢一次开几万个。

**补充**：Go 运行时把 M 个 goroutine 调度到 N 个 OS 线程上（N 默认等于 CPU 核数，由 `GOMAXPROCS` 控制），称 **M:N 调度**。所以 `go p.worker()` 开 3 个 goroutine，很可能只落在 1~2 个 OS 线程上。

### 🚩 术语红线

**本项目全程只有一个进程，里面跑的是 goroutine。**
把 goroutine 说成"进程"或"线程"，面试官会立刻判断你没搞懂并发模型——这是**一秒钟掉档**的错误，比答不出问题更致命。说之前先在心里过一遍这三个词。

## Q4.5 既然 goroutine 这么便宜，为什么还需要 worker pool 限制数量？

**考点**：能否区分"**开 goroutine 的成本**"和"**goroutine 干的活的成本**"。这是 pool 这个设计在简历上的真正卖点。

**我的原答**（⚠️ 结论对，术语错）：
> "最大进程为 3 个，避免太多进程占用过多资源。"（"进程"应为 goroutine，见上方术语红线）

**标准答法**：
> **限的从来不是 goroutine，是并发干活的数量。** goroutine 本身极便宜，但它干的活很贵：
>
> - M1 阶段（`time.Sleep` 模拟）：限的是内存和 CPU
> - M2 接入 LLM 后：限的是**同时在飞的 API 请求数**，直接决定
>   - 会不会被上游**限流**（HTTP 429）
>   - **烧钱速度**（token 消耗速率）
>   - 下游数据库/连接池会不会被打穿
>
> 去掉限制的后果不是"内存不够"，而是**上游服务把你整个 IP 封掉**，或者一夜之间账单爆掉。所以 pool 的 size 是一个**业务和成本参数**，不只是技术参数。

**常见追问**：
- *size=3 这个数字怎么定的？* → M1 是随手取的演示值。生产上应由上游的**速率限制（RPM/TPM）**反推，并做成配置项而非硬编码。
- *不用 pool，用带缓冲的 semaphore（`chan struct{}`）行不行？* → 行，`golang.org/x/sync/semaphore` 或容量为 N 的 channel 都能限并发。区别是 pool 的 goroutine **常驻复用**，semaphore 是**每任务新建** goroutine。任务极多且极短时 pool 更省；需要动态伸缩时 semaphore 更灵活。

## Q5 【陷阱题】队列满了之后 `Enqueue` 会发生什么？

**考点**：能否看见自己代码的**缺陷**。答得出来说明真懂这套架构的边界，而不只是"把它拼出来了"。

**我的原答**（⚠️ 机制对，但没把结论推到底）：
> "queue 是个 chan，size 由初始化决定，满了会卡在这里等待缓冲区腾出空间。"
> 追问后："handler 调用的入队，请求会卡在这里。"

**标准答法**——把后果链条讲完：
> `Enqueue` 是在 `HandleRun` 里被调用的，所以阻塞的是**处理该 HTTP 请求的 goroutine**（net/http 每个请求一个）。后果链条：
>
> 1. 队列满时，`HandleRun` 阻塞在 `p.queue <- id` 这一行
> 2. 后面的 `w.WriteHeader(202)` 永远执行不到
> 3. **用户的 HTTP 请求一直挂着转圈**，直到超时
> 4. 最讽刺的是：`store.Create` 已经执行完了，任务**已存在**且状态为 `pending`——但**用户永远拿不到那个 taskID**，因为响应发不出去
>
> **这把整套异步设计给毁了。** 做 202 的初衷就是"不让用户等"，结果队列一满用户又开始等——只是等的位置从"等任务完成"变成了"等排队位置"。

**修法**（承认缺陷 + 给方案，这才是完整回答）：
> 1. **快速失败**：`select` 加 `default` 分支，队列满立刻返回 `503 Service Unavailable`（配 `Retry-After` 头），让客户端重试。同时要**清掉 store 里那条已创建的 pending 记录**，否则会留下永远不会被执行的僵尸任务。
> 2. **持久化队列**：换 Redis / Kafka，把积压移出进程内存。附带解决另一个问题——当前实现**进程一重启，内存里的队列和 store 全部丢失**。

**常见追问**：
- *为什么用 503 而不是 429？* → 429 Too Many Requests 是"**你**请求太频繁了"（针对单个客户端），503 是"**我**现在处理不过来"（服务端整体过载）。队列满属于后者。
- *无缓冲 channel（size 0）会怎样？* → 每次 `Enqueue` 都必须等到某个 worker 正好在 `<-p.queue` 上等着才能交接，等于把队列容量降为 0，阻塞概率大增。缓冲区的作用就是吸收**突发流量**。

## 已知待改进项（面试主动提，是加分项）

| 缺陷 | 影响 | 修法 |
|---|---|---|
| 队列满阻塞 handler | 异步退化为同步 | `select` + `default` → 503 |
| store 为内存态 | 进程重启丢全部任务 | 持久化（SQLite / Redis） |
| 无 graceful shutdown | Ctrl+C 时在跑的任务直接丢 | `signal.NotifyContext` + `srv.Shutdown` |
| 无响应 `Location` 头 | 客户端需自己拼查询 URL | 202 响应加 `Location: /tasks/{id}` |
| pool size 硬编码 | 无法按环境调整 | 提为配置项 / 环境变量 |
